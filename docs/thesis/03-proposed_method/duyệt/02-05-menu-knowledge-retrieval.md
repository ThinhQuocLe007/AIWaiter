## 2.5 Menu Knowledge Retrieval (RAG)

> *Retrieval-augmented generation (RAG) grounds LLM outputs in domain-specific documents that were absent during training. This section surveys the RAG pipeline from the bottom up: why retrieval is necessary and how the standard architecture developed from naive embedding-based search into advanced and modular designs (§2.5.1); the embedding models, both dense bi-encoders and sparse keyword models, that turn text into searchable representations, together with the Vietnamese word segmentation that both paradigms depend on (§2.5.2); how those representations are stored in dense vector indices and sparse inverted indices and queried at runtime (§2.5.3); how results from several retrieval strategies are fused into a single ranking (§2.5.4); and the extensions proposed beyond the standard retrieve-then-generate paradigm, namely query rewriting, post-retrieval evaluation, and multi-turn search context, each evaluated in isolation and never composed into an architecture where the LLM actively controls retrieval quality (§2.5.5).*
>
> **Cross-refs:** §2.1 (overview: RAG limitations), §4.1 (FR2, menu search by attributes), §4.6 (knowledge retrieval pipeline: proposed method), §5.3.4 (retrieval evaluation)
> **Citations:** [2.5.1]–[2.5.40]; final numbering assigned when all Ch.2 references are merged.

### 2.5.1 The Knowledge Problem and Standard RAG

Large language models are trained on public web data frozen at a specific point in time. Domain-specific knowledge is absent from that distribution: a restaurant's menu, with its particular dish names, local ingredients, seasonal items, and precise pricing, appears nowhere in it. Asked about such knowledge without access to it, an LLM produces factually incorrect output with high confidence, a failure mode documented as closed-book hallucination [2.5.1]. Retrieval-augmented generation (RAG), introduced by Lewis et al. [2.5.2], separates knowledge from model parameters by inserting a retrieval step between the user's query and the LLM's generation. Offline, a knowledge corpus is split into document chunks, each embedded into a dense vector by a sentence encoder and stored in a vector index. Online, the user's query is embedded with the same encoder, the top-k documents with the most similar vectors are retrieved by similarity search, and those documents are injected into the LLM's prompt as grounding context. This architecture of embedding, retrieval, and generation has become the dominant approach for knowledge-intensive NLP tasks including open-domain question answering [2.5.3], fact verification [2.5.4], and domain-specific dialogue [2.5.5].

The standard pipeline, now called naive RAG in the survey literature [2.5.6], has been extended along two trajectories. Advanced RAG improves individual stages. Chunk optimization strategies such as semantic splitting and sliding-window overlap produce document segments with coherent semantic boundaries rather than arbitrary length-based cuts. Re-ranking models trained on retrieval relevance scores reorder the top-k retrieved documents to improve precision, at the cost of an additional inference step. Query expansion augments the user's query with synonyms, related terms, or sub-questions before embedding, which widens the retrieval net. These improvements are incremental. Each addresses a specific failure mode, whether poor chunk boundaries, imprecise ranking, or narrow queries, without changing the underlying architecture, and the LLM remains a downstream consumer of whatever retrieval returns.

Modular RAG [2.5.7] restructures the pipeline into independent, swappable modules, a retriever, a rewriter, an evaluator, and a generator, with configurable composition. The modularity allows per-domain optimization: a medical QA system might prioritize retrieval precision through aggressive re-ranking, while a creative writing assistant might configure the retriever for recall over precision. It also exposes a design question that naive and advanced RAG leave implicit: which modules should execute, in what order, and under what conditions? The literature documents the configurable composition [2.5.7] but not the coordination problem, that is, how a module should decide whether its output is adequate, whether to invoke another module, or whether to signal that retrieval has failed. The modules exist independently, and the control logic connecting them is absent from the documented architecture.

All three variants share a single structural assumption: the query embedding lies close to the relevant document embeddings in vector space. The assumption holds when the query and the target documents share vocabulary. It fails when the query expresses an information need through terms absent from the document corpus, a failure documented as query-document vocabulary mismatch [2.5.8]. The mismatch is structural rather than a matter of index quality, encoder choice, or chunk strategy, because the query vectors and the document vectors occupy disconnected regions of the embedding space. Improving any individual pipeline stage cannot repair it. What it would take is an architectural position that naive, advanced, and modular RAG do not provide: a component that inspects the query, recognizes the vocabulary gap, and transforms the query into terms the document space can match before retrieval executes.

One property is common to all three variants and is easier to see once they are set beside one another. In each, information flows in one direction: the query is transformed into a retrieval, the retrieval into a set of documents, the documents into a prompt, the prompt into text. The LLM occupies the last position in that chain. It receives whatever retrieval returned and generates from it, having had no part in deciding how the retrieval was conducted and no means of registering that what came back was unusable. Naive RAG establishes this arrangement, advanced RAG improves the quality of each stage within it, and modular RAG makes the stages swappable without altering the direction in which they are connected. The vocabulary mismatch described above is therefore a failure the architecture provides no position to detect, since detection would require the component best able to judge relevance to sit somewhere other than at the end.

### 2.5.2 Embedding Models

> *Embedding models convert text into representations that can be compared for relevance. Two paradigms have been studied. Dense embeddings produce continuous vectors in a learned semantic space; sparse embeddings produce high-dimensional term-weight vectors representing exact lexical content. Vietnamese word segmentation is a prerequisite for both, because without correct word boundaries each paradigm represents syllable fragments rather than lexical units. This subsection surveys segmentation tools, dense models, and sparse models as off-the-shelf components, and reports the properties on which a choice between them can be made.*

Vietnamese script places spaces between syllables, not between words. A three-syllable compound such as "bún bò Huế" is written as three space-separated tokens but is one lexical item, a specific spicy beef noodle soup. Without word segmentation both paradigms represent per-syllable fragments: a dense model embeds "bún", "bò", and "Huế" separately rather than the compound as a whole, and a BM25 index treats the three as independent terms, matching any document that contains any one of the syllables.

Three tools are documented for Vietnamese word segmentation [2.5.9]. `underthesea` applies a CRF segmentation model trained on the Vietnamese Treebank and outputs compound tokens joined by underscores. It reaches approximately 97% accuracy on the VLSP 2013 word segmentation benchmark for formal text, runs as a pure Python library with about 50 MB of model data, and is the most widely integrated option in the Vietnamese NLP ecosystem. `VnCoreNLP` is a Java pipeline covering segmentation, part-of-speech tagging, named entity recognition, and dependency parsing. Its richer feature set, which includes word embeddings and character-level RNN representations, yields higher documented accuracy than `underthesea` on formal Vietnamese text, at the cost of a Java runtime dependency that adds deployment complexity and per-call process overhead. `pyvi` is a lightweight pure-Python tokenizer using dictionary-based segmentation with regular-expression post-processing. Its accuracy is lower than the alternatives, with documented weakness on compound terms whose syllable boundaries are ambiguous, a limitation directly relevant to a retrieval domain dominated by compound dish names. No prior work has benchmarked segmentation accuracy on domain-specific proper nouns, where a segmenter's dictionary and statistical model are least reliable.

**Table 2.5a.** Vietnamese word segmentation tools.

| Tool | Method | Accuracy (VLSP 2013) | Deployment | Documented limitations |
|------|--------|:---:|---|---|
| `underthesea` | CRF, Vietnamese Treebank | ~97% | Pure Python, ~50 MB | Accuracy on informal and elided forms unbenchmarked; domain-specific proper nouns not evaluated |
| `VnCoreNLP` | RNN + word embeddings + CRF | Higher (~98%+) | Java (separate process) | Java runtime dependency; per-call process overhead compared with in-process alternatives |
| `pyvi` | Dictionary + regex | Lower | Pure Python, no model | Weak on compound terms with ambiguous boundaries; dictionary coverage limited |

Dense embedding models produce continuous vector representations through sentence encoders trained on paired or contrastive objectives. Two categories have been documented for Vietnamese text.

Vietnamese-native bi-encoders are trained specifically or predominantly on Vietnamese corpora. `bkai-foundation-models/vietnamese-bi-encoder` [2.5.10] uses a PhoBERT-base encoder [2.5.11] pre-trained on a 20 GB Vietnamese corpus and fine-tuned on Vietnamese sentence similarity pairs with L2 normalization. Its monolingual Vietnamese tokenizer preserves diacritics without the subword boundary artifacts that multilingual BPE tokenizers introduce, and its training corpus includes informal registers from social media and forums, so casual orthographic variants are better represented than in models trained only on formal text. `VoVanPhuc/sup-SimCSE-VietNamese-phobert-base` [2.5.12] applies the SimCSE contrastive learning framework [2.5.13] to PhoBERT and is evaluated on Vietnamese semantic textual similarity benchmarks. `AITeamVN/Vietnamese_Embedding` [2.5.14] uses a 1,024-dimensional space from a BART-based encoder, trading larger index size and longer search latency for higher representational capacity. On Vietnamese STS and ViText2Vec benchmarks [2.5.15] these models outperform multilingual alternatives by 8% to 15% on cosine similarity correlation. Retrieval-specific benchmarks, which measure precision and recall over document collections rather than sentence-pair similarity, are unreported for the category.

Multilingual models with Vietnamese capability achieve state-of-the-art results on cross-lingual retrieval benchmarks that include Vietnamese queries. `BAAI/bge-m3` [2.5.16] is a 568M-parameter model supporting over 100 languages, with native dense, sparse, and multi-vector retrieval in a unified architecture, and it currently ranks first on the MIRACL multilingual retrieval benchmark. `intfloat/multilingual-e5-large` [2.5.17] applies the E5 contrastive training recipe to a multilingual encoder and performs competitively on cross-lingual retrieval tasks. `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` [2.5.18] is a compact baseline at 384 dimensions and 118M parameters, widely integrated in RAG frameworks, with two documented weaknesses: its BPE tokenizer strips Vietnamese diacritics during subword tokenization, which collapses tonal distinctions into embedding noise, and its reduced dimensionality gives up representational resolution against 768-dimensional alternatives. Diacritic handling across this category is partial. The tokenizer preserves diacritic-bearing characters but allocates no attention specifically to tonal distinctions, and compound-word boundaries are not recognized as syntactic units distinct from syllable spans.

The two categories differ along a documented axis running from Vietnamese-language fidelity to ecosystem maturity. Vietnamese-native models handle diacritics better and are trained on Vietnamese-register text, but their retrieval performance is less documented and they lack features the multilingual alternatives provide natively, such as multi-vector retrieval and cross-lingual search. Multilingual models offer mature retrieval features and broad benchmark coverage, with Vietnamese diacritic handling that is adequate rather than optimized.

Where neither category is characterised is on the kind of corpus a menu constitutes. The cross-lingual retrieval benchmarks against which the multilingual models are evaluated, MIRACL and MTEB, are built from news articles and encyclopedia entries: documents of several hundred tokens whose vocabulary and term-frequency distributions approximate general language. A menu is the opposite kind of corpus in every respect that retrieval depends on. Its documents are short and structurally uniform, its vocabulary is dominated by proper nouns that appear in no general corpus, and the terms distinguishing two entries from one another may amount to a single word. No published retrieval evaluation, for either category of model, uses a corpus with those properties.

| `VoVanPhuc/sup-SimCSE-VietNamese-phobert-base` | 768 | ✓ | ✓ | ~135M | SimCSE contrastive training on PhoBERT; evaluated on Vietnamese STS | Encoder-only; less evaluated on retrieval tasks than on similarity tasks |

Sparse keyword models are the alternative paradigm to dense embeddings. Instead of learning a continuous semantic space, they represent documents as sparse vectors indexed by vocabulary terms, with weights set by term frequency and inverse document frequency statistics. BM25, introduced by Robertson and Walker [2.5.19], extends the TF-IDF framework with document-length normalization through two tunable parameters: k₁ controls term-frequency saturation, which stops a term appearing 50 times from being treated as 50 times more relevant than one appearing 5 times, and b controls the degree of length normalization, applied in full at b = 1 and removed entirely at b = 0. What BM25 does well is exact keyword matching: a document whose indexed terms match the query terms precisely scores high, with strong discriminability between documents that contain the terms and documents that do not. What it cannot do is bridge the vocabulary gap. A query containing no term present in the document index returns nothing, whatever the parameter tuning or term weighting, because a sparse representation has no mechanism for crossing a lexical gap.

For Vietnamese, BM25 effectiveness depends on word segmentation quality. If compound terms are split into independent syllable tokens, BM25 matches individual syllables that appear across unrelated documents. The query syllable "bò" then matches both "bún bò Huế", correctly, since the dish contains beef, and "bò lúc lắc", a completely different dish that also happens to contain beef, which produces false positives. If segmentation is too conservative, compound terms fail to match partial-name queries where the user supplies only the head noun. The interaction between segmentation quality and BM25 retrieval precision has not been systematically studied for Vietnamese domain-specific corpora.

**Table 2.5c.** BM25 parameters and their Vietnamese-specific considerations.

| Parameter | Role | Vietnamese-specific consideration |
|-----------|------|----------------------------------|
| k₁ (term frequency saturation) | Prevents a term appearing 50 times from scoring 50 times a term appearing 5 times. Typical range: 1.2 to 1.5 | No language-specific effect; standard IR parameter |
| b (length normalization) | Controls the document-length penalty: applied in full at b = 1, removed entirely at b = 0 | The penalty exists to stop long documents accumulating term matches by length alone. How much it matters is a property of the corpus rather than of the language, since it depends on how widely document lengths vary within the collection |
| Tokenization dependency | BM25 vocabulary is the set of tokens produced by the word segmenter. Mis-segmented compounds fragment into independent terms | Compound dish names must be preserved as single tokens; without correct segmentation, individual syllables match across unrelated documents |
| Strengths | Exact keyword matching with high discriminability between documents containing and not containing query terms | Effective for dish-name lookup when segmentation is correct |
| Limitations | Zero vocabulary overlap produces zero results regardless of parameter tuning | Sensory queries with no menu vocabulary return empty results; no mechanism to bridge the lexical gap |

### 2.5.3 Indexing and Search

> *Once text is converted into representations, whether dense vectors from a bi-encoder or sparse term-weight vectors from BM25, those representations have to be stored in a searchable index and queried efficiently. The indexing strategy follows from the representation type: dense vectors need a vector index supporting similarity search over continuous spaces, and sparse vectors need an inverted index mapping vocabulary terms to document postings. Both paradigms are mature off-the-shelf technologies with well-documented performance characteristics.*

Dense vector indexing is dominated by FAISS (Facebook AI Similarity Search), introduced by Johnson et al. [2.5.20]. FAISS provides a family of index structures spanning the accuracy-speed trade-off. At one end, `IndexFlatL2` compares the query vector exhaustively against every stored vector, computing exact Euclidean distances. It is deterministic, since the same query always returns the same results, and sufficient for small corpora of a few hundred to a few thousand documents, where the O(n) per-query cost is negligible. At the other end, approximate indices such as `IndexIVFFlat` partition the vector space into Voronoi cells by k-means clustering and search only the cell closest to the query vector and its neighbours, which reduces search complexity to sub-linear at the cost of a small probability of missing the true nearest neighbour. `IndexHNSW` builds a navigable small-world graph over the vectors and searches it by greedy traversal in logarithmic time. The distance metric, whether cosine similarity via L2 distance on normalized vectors, inner product for unnormalized representations, or Euclidean distance, defines what "similar" means in the vector space. FAISS stores both the vector and a back-reference to the original document, and retrieval returns the document with a similarity score.

Sparse inverted indexing maps each vocabulary term to a postings list, the set of documents containing that term, each annotated with term frequency, positions within the document, and any payload data. At query time the query is tokenized into terms, the postings list for each term is retrieved, and BM25 scoring is computed over the intersection of query terms and document postings. The inverted index is the foundational data structure of information retrieval, validated across decades of evaluation at TREC, CLEF, and NTCIR [2.5.21], and its performance characteristics are well understood: index construction is O(n) in the number of documents, query time is O(|Q| × avg_posting_length) for |Q| query terms, and memory footprint is proportional to vocabulary size and average document length. For Vietnamese the vocabulary depends on segmentation quality, since mis-segmented compound terms fragment into several postings lists, which inflates index size and dilutes term specificity.

**Table 2.5d.** Dense and sparse indexing compared.

| Property | Dense (FAISS) | Sparse (inverted index) |
|----------|:---:|:---:|
| Search mechanism | Similarity search in continuous vector space: cosine, inner product, or Euclidean distance | Term intersection over postings lists with BM25 scoring |
| Index types | Flat (exact, O(n)), IVF (approximate, sub-linear via clustering), HNSW (approximate, logarithmic via graph traversal) | Postings lists with per-document term frequency and position data |
| Determinism | Flat search is deterministic; approximate indices trade deterministic correctness for speed | Deterministic for a given tokenization |
| Corpus scale | Flat sufficient for small corpora (hundreds of documents); approximate indices for large scale | Efficient at any scale; construction O(n), query O(\|Q\| × avg_posting_length) |
| Vocabulary-gap handling | Encoder-dependent: the embedding model determines whether a query with no lexical overlap can still retrieve relevant documents | None; zero vocabulary overlap produces zero results |
| Vietnamese dependency | Embedding model choice determines diacritic sensitivity and compound-word representation quality (§2.5.2) | Word segmentation quality determines whether compound terms are single indexed tokens or fragmented syllables (§2.5.2) |

### 2.5.4 Result Fusion

> *When several retrieval strategies run in parallel, a dense FAISS search and a sparse BM25 search for instance, they produce separate ranked lists that have to be combined into one ranking. Fusion methods exist because scores from different retrievers are incommensurable: BM25 scores are unbounded term-weight sums, cosine similarities are bounded in [−1, 1], and the two numeric ranges carry no common meaning. This subsection surveys three fusion techniques from the information retrieval literature, each handling the incommensurability differently.*

Reciprocal Rank Fusion (RRF), introduced by Cormack et al. [2.5.22] for meta-search evaluation, avoids the score normalization problem by operating on document ranks rather than raw scores. For each document the fused score is the sum of the reciprocal of its rank in each constituent result list, shifted by a constant k: score(d) = Σ 1 / (k + rankᵣ(d)), where k is typically set to 60. A document ranked first in both retrievers receives 1/61 + 1/61; a document ranked first in one retriever and absent from the other receives 1/61 and nothing more. RRF needs no score normalization, no domain-specific parameter tuning, and no assumption about score distributions. The constant k controls the influence of high-ranked against low-ranked documents: at k = 60 the score difference between rank 1 (1/61 ≈ 0.0164) and rank 5 (1/65 ≈ 0.0154) is about 6%, which reflects the design principle that the top several results from each retriever should contribute with comparable weight. A document appearing in only one result list is not penalized beyond the missing contribution from the other retriever, and can still rank highly if its single-list rank is competitive.

Linear combination handles fusion by normalizing scores and then summing them with weights: score(d) = α × normalize(s₁(d)) + (1 − α) × normalize(s₂(d)). It requires per-retriever score normalization, typically min-max scaling to [0, 1] or z-score standardization, and a domain-tuned weight α controlling the relative contribution of each retriever. Where α is well calibrated for a specific domain and document collection, linear combination can achieve higher accuracy than RRF, because it exploits the score magnitude information RRF discards [2.5.23]. The optimal α does not transfer across domains or document collections, though. A weight tuned on news articles will not be optimal for menu entries, and the method is sensitive to the choice of normalization scheme. Without domain-specific calibration data, linear combination can underperform RRF, because score magnitude differences between retrievers that carry no meaningful signal are amplified by the weight.

Condorcet voting [2.5.24] treats fusion as a pairwise comparison problem: for every pair of documents in the union of the result lists, the document ranked higher in more retrieval lists wins the pairwise comparison, and the fused ranking sorts documents by number of wins. The method requires no score normalization and extends naturally to consensus across more than two retrieval lists. Its computational cost is O(n²) in the number of unique documents across all result lists, which is manageable for small n (tens of documents) and prohibitive when result lists are long. For two-retriever fusion specifically, no evaluation has demonstrated a systematic accuracy advantage over the simpler and faster RRF baseline.

**Table 2.5e.** Fusion methods for combining ranked lists from several retrievers.

| Method | Score normalization | Domain transfer | Computational cost | Single-list documents |
|--------|:---:|:---:|:---:|---|
| RRF | Not required; operates on ranks | Domain-independent (k = 60 is fixed; no per-domain tuning needed) | O(n log n) for sorting n unique documents | Receive contribution from one retriever; no penalty for absence from other lists |
| Linear combination | Required; min-max or z-score per retriever | Weight α must be re-tuned per domain and document collection | O(n) after normalization | Score depends on normalization of the present retriever; absent retriever contributes 0 |
| Condorcet voting | Not required; uses pairwise rank comparisons | Domain-independent | O(n²) for n unique documents | Win against documents ranked lower in all lists where both appear; absent documents lose all pairings |

### 2.5.5 Beyond Retrieve-then-Generate: Rewriting, Evaluation, Context

> *The standard RAG pipeline, which embeds the query, retrieves documents, and generates, operates in one direction. Retrieval produces a ranked list; the LLM consumes that list and produces text. There is no architectural position for inspecting retrieval quality, for deciding that the retrieved documents are insufficient, or for feeding a quality signal back to trigger a different retrieval strategy. Three classes of extension have been proposed against pieces of this limitation: pre-retrieval query transformation, post-retrieval result evaluation, and multi-turn search context persistence. Each has been evaluated as an independent point solution on English benchmarks, and none addresses the interaction between rewriting, retrieval, evaluation, and context inside a single pipeline where the LLM actively controls retrieval quality.*

Pre-retrieval query rewriting transforms the user's query before it reaches the retriever. Three techniques are documented, each bridging the vocabulary gap between query and documents by a different mechanism.

HyDE (Hypothetical Document Embeddings), introduced by Gao et al. [2.5.25], prompts an LLM to generate a plausible relevant document and embeds that hypothetical document for retrieval in place of the raw query. The premise is that LLM-generated text, even where factually wrong, shares vocabulary and structure with real documents in the target corpus, while the user's natural-language query may come from a different register. Evaluated on TREC DL and Web Questions, HyDE improved retrieval recall on vocabulary-gap queries in English. Its documented limitation is unbounded generation: the LLM may fabricate terms, entities, or categories absent from the real corpus, and the hypothetical document's embedding then pulls retrieval toward the fabrication rather than toward genuinely relevant documents. The technique gives the LLM no way to inspect whether the rewritten query improved retrieval, since the generation runs one way, from LLM to retriever.

Step-Back Prompting, introduced by Zheng et al. [2.5.26] for reasoning tasks and later adapted to retrieval, takes a different route. Rather than generating a hypothetical document, the LLM abstracts the query to a higher conceptual level and retrieves against the abstraction. An implementation might abstract "món gì ấm bụng cho ngày lạnh" to "món nước nóng, lẩu, súp, cháo", the categories of food that satisfy the sensory description, expressed in terms the retriever can match. The approach reduces HyDE's hallucination risk, because the LLM produces keywords and category labels rather than free-form documents, but it depends on the LLM identifying the right level of abstraction: too abstract and retrieval loses specificity, too specific and the vocabulary gap persists. It has been evaluated on MMLU and TimeQA in English. No evaluation exists for Vietnamese, where the LLM's cultural associations, meaning the mapping from sensory experience to culinary category, are less grounded than its English factual knowledge.

Query2Doc [2.5.27] combines both strategies: the LLM generates a rewritten query string and a hypothetical document, and their embeddings are concatenated for retrieval. This draws on the complementary strengths of keyword rewriting, which contributes precision from targeted terms, and hypothetical document generation, which contributes recall from shared vocabulary structure. Its documented limitation is computational cost, since two LLM inference calls per retrieval operation create a latency barrier for real-time deployment.

All three techniques share a structural property that keeps them out of a control loop: they transform the query and then hand off to retrieval, with no return path. The LLM that performed the rewriting never sees the retrieved results, cannot evaluate whether the rewrite helped or hurt, and cannot adjust its strategy from retrieval quality. The rewriting is an open-loop transformation.

Post-retrieval evaluation inspects the retrieved documents after retrieval and before generation, filtering noise and, in some architectures, triggering corrective action.

Self-RAG, introduced by Asai et al. [2.5.28], uses reflection tokens, special tokens the model learns to generate during fine-tuning that indicate whether each retrieved passage is relevant to the query and whether the generated text is supported by it. Quality assessment is embedded in the generation process itself, which allows per-passage relevance filtering without a separate evaluation model. Its primary limitation is the fine-tuning requirement: the reflection tokens have to be trained into the model's vocabulary and output distribution, which takes training infrastructure and labelled data that most domain-specific deployments do not have.

CRAG (Corrective RAG), introduced by Yan et al. [2.5.29], scores relevance at inference time without fine-tuning. The LLM rates each retrieved document on a numeric relevance scale, documents below a threshold are discarded, and if nothing passes the threshold a fallback is triggered, typically a web search or an alternative retrieval strategy. The approach adds one LLM inference call per retrieval operation. It has been evaluated on English QA benchmarks including PopQA, PubHealth, and Arc-Challenge, and its effectiveness depends on the LLM scoring relevance correctly for the target domain and language. The technique performs the evaluation, but its corrective action is predetermined rather than strategy-aware: the fallback is a web search, and the LLM does not decide what kind of search to run next or how to modify its approach.

FLARE (Forward-Looking Active Retrieval augmented generation) [2.5.30] interleaves generation and retrieval. As the LLM generates text token by token it monitors its own confidence, and on reaching a token it is uncertain about it pauses generation, retrieves additional information related to the uncertain span, and resumes with the new context. The technique is designed for long-form generation tasks, where the information need emerges progressively during writing. Its computational cost, several retrieval calls interleaved with generation steps, makes it unsuitable for latency-constrained settings where every retrieval call adds measurable delay.

All three post-retrieval techniques have been evaluated on English question-answering and fact-verification benchmarks, where relevance is a function of factual accuracy. None has been evaluated on domain-specific retrieval where relevance depends on structured metadata matching, that is, on whether a dish's ingredients, taste profile, and preparation method fit a sensory description, rather than on factual concordance with a knowledge base.

Multi-turn search context addresses a limitation specific to conversational retrieval: within a single dialogue session, the user may issue several retrieval queries that are semantically related to prior turns. A user who searches for a term in turn 3 and then refers to it pronominally in turn 6 ("cái đó có cay không?") expects the system to resolve the reference against prior search results rather than run a new retrieval on the literal query string "cái đó có cay". Dialogue state tracking, a well-established approach for task-oriented dialogue systems [2.5.31], maintains structured per-session state such as slot values, dialogue acts, and user goals, but it is designed for finite-state or frame-based architectures and is not natively integrated with RAG retrieval pipelines, where what is retrieved (a ranked list of documents with metadata) is larger and more structured than a scalar slot value. Memory-augmented RAG architectures including MemoryBank [2.5.32] and LongMem [2.5.33] persist retrieved context across conversations using vector databases or compressed summaries, but they are built for cross-session user modelling, remembering a user's preferences over weeks, rather than for within-session retrieval deduplication. No prior RAG extension addresses the entity resolution problem specific to multi-turn retrieval: determining whether a new utterance refers to a previously retrieved item and answering from memory instead of re-querying.

Each of these three extensions has been evaluated independently, as a point improvement on the standard pipeline, on English benchmarks. Set beside one another, they share a property that none of them individually reveals. Query rewriting acts before retrieval and hands off without a return path. Post-retrieval evaluation acts after retrieval and, where it takes corrective action at all, takes one that was fixed in advance rather than chosen in response to what was retrieved. Multi-turn context persists across turns without informing the retrieval that occurs within any of them. Each attaches to an edge of the pipeline, and none produces a signal that travels from the output of retrieval back to its input.

That absence is what keeps the arrangement one-directional despite the additions. A pipeline with all three extensions installed still cannot register that a retrieval was unsuccessful and then do something different in consequence, because registering it and acting on it are separate capabilities and no extension supplies the connection between them. Whether that connection is constructible, and if so which component is positioned to judge, given that judging requires understanding both the information need and the documents returned, is not a question the surveyed work takes up.

The components surveyed in §2.5.2 through §2.5.4, the segmenters, encoders, indices, and fusion methods, are individually mature, and the properties on which they differ are documented. The architecture that assembles them is where this survey finds less than it expected to.

It is worth noting where that architecture came from. Modular RAG was proposed to solve a real problem: the naive pipeline was rigid, and making its stages independent and swappable allowed each to be optimized for a domain without disturbing the others. Independence was the point. But independence was achieved by specifying what each module exchanges with its neighbours and leaving unspecified what any module should do about what it receives, so a module that produces poor output and a module that produces good output present the same interface. The pattern that made the components composable is therefore also the pattern that omits the question of coordination, which is why the extensions surveyed in §2.5.5 attach so readily to the pipeline's edges while none of them closes it. Each is a well-behaved module, and what the pipeline lacks is a component that is not one: something that reads the output of a stage and decides what the pipeline does next.

The vocabulary mismatch of §2.5.1 gives the difficulty its concrete form. A query phrased in sensory terms and a corpus indexed by name and category occupy disconnected regions of any representation, and no encoder, index, or fusion method operating on that query alone will bridge the distance. Bridging it requires knowledge about the domain, and in the surveyed pipeline the only component holding that knowledge is the one placed last and consulted never.
