## 2.4 Conversational AI Agent

> *A restaurant agent has to understand Vietnamese speech, decide on an action, and execute that action correctly, without inventing dish names or breaking the order process. This section surveys the components of task-oriented conversational agents: the architectures that orchestrate LLM-tool interaction (§2.4.2), the LLM reasoning engine (§2.4.3), intent classification to determine which tool an utterance demands (§2.4.4), action validation to keep hallucinated arguments from reaching external tools (§2.4.5), memory and state management (§2.4.6), and planning, tool composition, and domain adaptation (§2.4.7).*

### 2.4.1 From General-Purpose LLM to Task-Oriented Agent

The Transformer architecture, introduced by Vaswani et al. [2.4.1], replaced recurrent sequence processing with self-attention, which allows a model to capture long-range dependencies without the sequential bottleneck of an LSTM. Scaling these architectures along parameter count, training data volume, and compute produced large language models (LLMs) whose performance on language tasks improved in a predictable power-law relationship [2.4.2]. Trained on next-token prediction over web-scale corpora, these models turned out to be capable of translation, summarization, reasoning, and instruction following without being trained for any of them individually [2.4.3].

Whatever they can generate, LLMs remain text-in-text-out systems. They cannot modify a database, update application state, or command an external device. They map input tokens to output tokens, and those output tokens sit in a buffer until external code acts on them. The earliest way of bridging that gap was post-hoc parsing: the LLM produced a free-text instruction such as "add Ốc Hương to the cart," and a downstream parser, usually regex patterns, keyword matching, or a separately trained classifier, extracted the structured intent [2.4.4]. The pipeline was brittle, because the parser had to anticipate every phrasing the LLM might produce, and any variation broke the extraction.

Function calling [2.4.5] removed that fragility by making structured invocation a first-class capability of the LLM API itself. Instead of relying on a downstream parser, the LLM is given a schema of the available tools, each with a name, a natural-language description, and a typed JSON Schema for its parameters, and it produces a structured invocation object such as `{"name": "search", "arguments": {"query": "Ốc Hương"}}`. The serving framework intercepts that output, checks that it is syntactically correct, executes the corresponding function against live systems, and feeds the return value back to the LLM for the next reasoning step. Introduced by OpenAI and since adopted across Anthropic, Google, and Ollama [2.4.6], function calling is now the standard mechanism for turning LLM output into system actions. Figure 2.7 illustrates it.

**[Figure 2.7. Function calling mechanism: the LLM receives a tool schema alongside the conversation and produces a structured JSON invocation rather than a free-text description; the framework executes the tool and feeds the result back.]**

Function calling provides the mechanism for action. It does not guarantee correctness. An LLM can invoke the right tool with hallucinated arguments, call tools in an invalid sequence, or produce parameter values that violate domain constraints. Whether tool invocations are safe in a transactional domain, where an error has material consequences, is settled by the layers around the LLM: the orchestration architecture, the routing mechanism, the validation gates, the memory system, and the planning logic. The subsections that follow survey each of them.

### 2.4.2 Agent Architectures: The Orchestration Layer

The architecture surrounding the LLM determines when tools can be invoked, what happens between invocations, and what the system guarantees about correctness and termination. The agent development literature has studied four architectural patterns, each governing LLM-tool interaction differently.

The simplest is the chain, in which the developer declares a fixed linear sequence of steps (classify the utterance, extract parameters, call a tool, generate a response) with no branching. As implemented in LangChain's LCEL [2.4.7], each utterance type follows its own predetermined chain, so the control flow is explicit and the execution trace is fully auditable. Prior work on chain-based task-oriented dialogue [2.4.8] reports reliable execution for narrow domains with predefined workflows. What the chain buys is deterministic governance: the developer hard-codes every step, transition, and termination condition. What it costs is rigidity. A routing error at step one is unrecoverable, because no architectural component inspects the utterance mid-chain and redirects it, and error recovery means enumerating every possible failure mode at every step, which becomes combinatorial once the input space is open-ended natural language.

The autonomous reasoning loop, introduced by the ReAct pattern [2.4.9], addresses the chain's inability to adapt to conversational variation by delegating governance to the LLM itself. On each iteration the model receives the current state (conversation history, tool definitions, and prior tool results) and produces either a reasoning trace, a tool call, or a final answer. The framework executes any tool call, feeds the result back into the loop, and the next iteration begins. AutoGPT [2.4.10] extended the pattern with internet access, file system operations, and long-term memory, which let agents pursue open-ended goals across dozens of iterations without human intervention. The loop is conversationally flexible: the LLM chooses its next action from what it observes, and the developer never enumerates dialogue paths.

That flexibility is bought by giving up the deterministic governance a chain provides. Termination is not guaranteed. The loop ends when the LLM decides to stop, and if the model enters a reasoning cycle, producing neither a tool call nor a final answer, the turn blocks indefinitely [2.4.11]. Nothing in the architecture enforces a valid tool sequence or checks tool arguments before execution. ReAct has been evaluated on knowledge-intensive benchmarks such as HotpotQA and FEVER [2.4.9], where it improved task completion rates over chain-based baselines. Its published limitations note that the architecture cannot guarantee bounded execution or action correctness, because governance and proposal reside in the same probabilistic component.

Graph-based architectures, as implemented in LangGraph [2.4.12], restore deterministic governance by encoding the state machine in the topology of the architecture rather than in prompt instructions. The developer declares a directed graph: a typed, shared state object flows through nodes (LLM calls, tool executions, or deterministic functions) connected by conditional edges that inspect the state and determine which node executes next. Unlike a chain, the graph can branch on runtime conditions. Unlike a loop, termination is structural, guaranteed by the graph topology rather than emerging from the LLM. The architecture provides three primitives: a checkpointer that serializes state after each node execution for session-scoped persistence [2.4.13], conditional edges that allow a mandatory validator node on every path between an LLM call and a tool execution, and circuit breakers that bound execution by capping retry iterations before routing to a fallback response. LangGraph has been evaluated primarily on code generation and multi-step reasoning tasks [2.4.12]; its applicability to task-oriented dialogue in Vietnamese has not been assessed.

Multi-agent architectures such as AutoGen [2.4.14], CrewAI [2.4.15], and CAMEL [2.4.16] decompose the single-agent model, distributing tools, prompts, and responsibilities across independent LLM instances that communicate through structured messages. AutoGen supports hierarchical delegation, where a manager LLM routes tasks to specialized workers; CAMEL introduced role-playing LLM pairs for task simulation and synthetic data generation. The argument for the decomposition is specialization: each agent operates with a narrower scope and a more focused prompt than a single agent handling all tools, which the literature suggests should produce more reliable behavior inside each agent's bounded domain [2.4.14]. Three limitations are documented. One is attention dilution [2.4.17]: as agents exchange messages, each agent's context window accumulates not only the user utterance but every peer agent's reasoning traces, tool outputs, and coordination instructions, and benchmarks record accuracy regression once the agent count passes two or three. Another is that coordination is entirely LLM-mediated, since the manager invokes an LLM to decide which worker to route to and workers invoke LLM calls to hand off to peers, which leaves no deterministic coordination layer. The third is that ownership of the business process is diffused across agents: no single component is structurally responsible for the correctness of the overall tool sequence.

Graph-based architectures supply the primitives for combining deterministic governance with LLM flexibility, namely conditional edges for mandatory validation, circuit breakers for bounded execution, and checkpointers for session persistence, but their application to a domain where every LLM-proposed action must be inspected before execution has not been studied. Multi-agent architectures have been evaluated on cooperative reasoning tasks [2.4.14] but not on Vietnamese dialogue, and the documented attention dilution problem [2.4.17] has not been characterized for task-oriented agent coordination.

### 2.4.3 Large Language Models: The Reasoning Component

The LLM is the component that reads user input, conversation history, and system prompts and decides which tool to call and with what arguments. The literature documents three categories of Vietnamese-capable LLM, each trading language quality, function-calling capability, and deployment model against one another. Two further properties cut across the categories: the context window sets the maximum input a model can process in a single forward pass, and the serving framework determines how the model is deployed and at what cost.

The most direct approach to Vietnamese dialogue is a model trained on Vietnamese. PhoGPT (7B) [2.4.18] is a decoder-only Transformer trained from scratch on a Vietnamese-dominant corpus. On Vietnamese-specific benchmarks including VLSP [2.4.19] it produces grammatically fluent output with correct tonal diacritics and the politeness particles (dạ, ạ) that multilingual models often flatten or omit. ViSoBERT [2.4.20] is an encoder-only model based on BERT, aimed at classification and embedding rather than text generation. What these models offer is language quality: Vietnamese is their first language, in a way it cannot be for a multilingual model where Vietnamese competes with dozens of others for representation. What they lack is function calling as a first-class API capability. As of 2025, neither PhoGPT nor ViSoBERT can produce the structured `{"name": "...", "arguments": {...}}` invocation format that agent frameworks intercept and execute. They can describe in free text what action should be taken, so deploying them in a task-oriented agent would mean reverting to the post-hoc parsing architecture described in §2.4.1.

Open-weight multilingual models make the opposite trade, giving up Vietnamese-specific optimization for ecosystem maturity while remaining self-hostable. The Qwen2.5 series (0.5B to 72B parameters) [2.4.21] emphasizes Southeast Asian languages in its training data composition and has been evaluated on multilingual benchmarks that include Vietnamese conversation. Llama 3 (8B to 405B) [2.4.22] contains approximately 0.5% Vietnamese text in its 15-trillion-token training corpus. Gemma 2 (2B to 27B) [2.4.23] supports Vietnamese as part of its multilingual training. All three families expose function calling as a documented API feature, assessed through the Berkeley Function Calling Leaderboard (BFCL) [2.4.24], a standardized benchmark measuring structured tool invocation accuracy across model families. Reported results separate the families consistently at the 7B to 9B scale, and the ordering is stable across leaderboard revisions even though the absolute figures are not: the leaderboard's scoring has changed across versions, so any specific percentage must be quoted against the version that produced it. What these models give up is Vietnamese quality. Their output is correct but sometimes stilted, with occasional diacritic errors and a tendency toward a neutral register rather than a context-appropriate polite one.

Commercial API models sit at the top of the accuracy range. GPT-4o, Claude 3.5 Sonnet, and Gemini 2.0 Flash [2.4.25]–[2.4.27] combine the highest documented Vietnamese conversational quality with the highest reported BFCL results, so they satisfy language quality and function-calling accuracy at the same time, without the compromise the open-weight multilingual models make. What they impose is a deployment model: every inference call requires internet connectivity, per-token costs accumulate with usage volume, and user data travels to servers outside the operator's control.

Context window size varies by an order of magnitude across these categories. PhoGPT provides 4,096 tokens [2.4.18], enough for single-turn exchanges but documented as insufficient for extended multi-turn dialogue [2.4.19]. Open-weight multilingual models span 8,192 tokens (Llama 3 8B, Gemma 2 9B) to 32,768 tokens (Qwen2.5 7B), with larger variants reaching 128K [2.4.21]–[2.4.23]. Commercial API models offer 128K to 1M tokens [2.4.25]–[2.4.27]. Two documented findings bound the practical significance of those differences. Liu et al. [2.4.28] showed that model performance degrades on information positioned in the middle of a long context regardless of total capacity, the "lost in the middle" phenomenon, and Xiao et al. [2.4.29] showed that transformer attention favors tokens at context boundaries. Both apply across all model sizes and categories. Vietnamese adds a further factor. Multilingual subword tokenizers are fitted predominantly on high-resource languages, so Vietnamese diacritics and compound words segment into more tokens than their English equivalents, and a context window of a given nominal size therefore holds less Vietnamese conversation than the figure suggests. The size of that penalty is tokenizer-specific and is not reported for the models surveyed here [2.4.61].

Three serving frameworks appear in the deployment literature for open-weight models. Ollama [2.4.30] runs a local HTTP server with an OpenAI-compatible API, designed for single-GPU deployments and keeping the model resident in GPU memory between requests. vLLM [2.4.31] targets higher throughput through PagedAttention, a key-value cache management scheme that lets concurrent inference requests share GPU memory without the overhead of separate model instances. llama.cpp [2.4.32] takes a different route: GGUF quantization at 4 to 8 bit precision supports CPU-first inference with optional GPU offloading, trading output quality for reduced VRAM requirements. That quality loss has been documented to fall disproportionately on languages underrepresented in training data [2.4.33], which matters for Vietnamese, where tonal diacritic distinctions are the fine-grained signal most exposed to quantization noise.

The three documented properties, function-calling support, context window capacity, and Vietnamese language quality, have been evaluated independently across model families but never jointly for a single application domain. The BFCL [2.4.24] measures tool-calling accuracy on general-domain function sets in English, and no equivalent benchmark exists for domain-specific tool invocation in Vietnamese, where tool arguments include compound dish names with tonal diacritics and informal variants. Vietnamese-specific models such as PhoGPT have been evaluated on NLU benchmarks (VLSP, translation, summarization) [2.4.19] but not on function-calling tasks. The context window studies [2.4.28]–[2.4.29] characterize attention behavior on English and multilingual corpora and do not account for the higher token consumption of Vietnamese text.

### 2.4.4 Intent Classification: The Routing Layer

Before an agent can invoke a tool, it has to determine which tool the customer's utterance demands. A routing error, such as sending a menu search utterance to the ordering subsystem, produces irrelevant results at best and incorrect system actions at worst. The task-oriented dialogue literature has studied five approaches to intent routing.

The earliest, deployed in platforms such as Rasa [2.4.34] and Dialogflow [2.4.35], uses supervised classifiers: keyword matching, an SVM over n-gram features, or an LSTM sequence tagger trained on labeled utterance-intent pairs. These are fast (~5ms) and deterministic, and have been deployed at scale for restaurant ordering in English, Chinese, Korean, and Japanese. Each classifier is language-specific, since keyword lists and n-gram features are manually curated, and informal variants such as teencode abbreviations fall out of vocabulary for a model trained on formal corpora. They also carry no conversation state: text features alone cannot separate a confirmation from a greeting, because both produce identical n-gram vectors.

Lightweight neural classifiers such as fastText [2.4.36] and SetFit [2.4.37] improve on the classical approaches with subword n-gram features and few-shot fine-tuning of sentence transformers. Subword features give partial robustness to previously unseen words, and inference stays fast (2 to 10ms) and deterministic. They share the limitation of every text-only approach: each utterance is processed in isolation, with no access to prior turns or dialogue state.

Semantic centroid routing [2.4.38] encodes each intent as the mean embedding of several labeled example utterances and classifies a new input by cosine similarity to those centroids. Because the same embedding model processes the training examples and the user utterance, new vocabulary is encoded in the same space without retraining. Inference takes roughly 15ms after embedding. Published accuracy on domain-specific classification benchmarks ranges from 75% to 90% [2.4.39], and the failures concentrate in three patterns: informal variants produce embeddings far from their formal centroids, context-dependent utterances sit roughly equidistant from several centroids, and multi-intent utterances produce a blended embedding that matches none of them.

LLM-based routing [2.4.40] hands classification to the LLM, prompting it with the utterance, the conversation history, and a list of intents. Because the model met informal Vietnamese during pretraining and can attend to prior turns injected into the prompt, it handles teencode, context-dependent ambiguity, and multi-intent compounding, which are the three patterns centroid routing fails on. The documented cost is latency and non-determinism: a single classification call takes 1.5 to 2.0 seconds on consumer GPU hardware, and temperature sampling means the same utterance may route differently across calls. A less explored variation, documented in prior work on utterance rewriting [2.4.41], uses the LLM only to decompose complex or ambiguous utterances into simpler fragments and leaves the intent assignment per fragment to a separate, faster classifier. This decomposition-only use has been demonstrated on English multi-intent utterances but has not been evaluated for Vietnamese, where sentence boundaries are less clearly marked and teencode compounding creates ambiguous segmentation points.

Each of the five approaches covers part of the routing requirement and fails elsewhere. Keyword-based and lightweight neural classifiers provide speed and determinism but stay blind to informal language, conversation context, and multi-intent utterances. Semantic centroid routing handles domain vocabulary through a shared embedding space and then breaks on the same three patterns that characterize Vietnamese restaurant speech. LLM-based routing resolves all three but costs 1.5 to 2.0 seconds per call and returns non-deterministic output under temperature sampling. The decomposition-only variant [2.4.41] cuts the LLM's role down to utterance splitting and keeps the speed of a separate classifier, but has not been evaluated on Vietnamese, where teencode compounds create ambiguous segmentation boundaries. State-augmented classification [2.4.42] adds dialogue context to a fast classifier, has been assessed only on English benchmarks, and would need a labeled Vietnamese dataset with state annotations that does not exist.

Across all five, the same trade recurs. The mechanisms that are fast and deterministic are precisely those blind to informality, dialogue context, and multi-intent structure, and the one mechanism that handles all three is slow and non-deterministic. The surveyed work treats this as a property of the choice itself, positioning the approaches along a single axis running from cheap and brittle to expensive and flexible. What it does not ask is whether the two halves of that trade are separable: whether the cases that defeat a classifier are frequent enough, or distinguishable enough in advance, to warrant a different mechanism from the cases that do not. The existing evidence for Vietnamese could not settle the question either, since compound dish names, tonal diacritics, context-dependent affirmations, and teencode abbreviations each aggravate a different one of the five documented limitations, and no approach has been evaluated on speech carrying those properties.

### 2.4.5 Action Validation: The Safety Layer

Correct routing ensures the right tool is called. It does not ensure the tool is called with correct arguments. An LLM that routes an utterance to the ordering subsystem may still produce `add_cart(name="Pizza Hải Sản", quantity=1)`, a call that is syntactically valid JSON and semantically wrong, because the named dish does not exist on the menu. Function calling guarantees syntactic validity; semantic correctness requires a separate mechanism. Three approaches to argument-level errors have been studied, each intervening at a different point in the generation pipeline [2.4.42].

The earliest and simplest defense is constrained decoding [2.4.43], which enforces JSON schema compliance at the token generation level: the serving infrastructure restricts the LLM's output vocabulary at each generation step to tokens consistent with the target schema, so field names, types, required fields, and value constraints match the tool definition. The guarantee is syntactic. `{"name": "Pizza Hải Sản", "quantity": 1}` satisfies every schema constraint, because `name` is a valid string and `quantity` a valid integer, and neither value has been checked against any external source of truth. Constrained decoding can stop the LLM producing a malformed tool call. It cannot stop it producing a well-formed call with wrong arguments.

Retrieval-augmented generation grounding [2.4.44] addresses the semantic gap that constrained decoding leaves open by injecting the authoritative data, for a restaurant the actual menu, into the LLM's prompt before it generates tool arguments. With valid dish names and prices in the prompt, the model is more likely to reproduce those exact strings than to fabricate alternatives. Asirvatham et al. [2.4.45] demonstrated that RAG grounding reduces hallucination rates in knowledge-intensive tasks without eliminating them: the LLM may attend to the wrong portion of the prompt, prioritize pretraining knowledge over the injected context, or select a nearby but incorrect value from the retrieved data. Grounding lowers the probability of error and supplies no mechanism for detecting which specific tool calls remain incorrect, so the system cannot distinguish a grounded correct call from an ungrounded hallucination.

Human-in-the-loop approval [2.4.46] attacks the same problem from the other end. Rather than preventing or reducing errors during generation, it requires a human operator to review each tool call before execution and either approve or reject it. Hallucination risk disappears, since every argument is verified against a person's knowledge of the domain and no incorrect call reaches an external system. The approach has been deployed in high-stakes decision-support systems where the cost of an error justifies the cost of human review [2.4.46]. What it gives up is not accuracy but autonomy: the system requires human staffing for every action, which limits it to domains where full automation is not the objective.

All three share a structural property that limits their effectiveness for autonomous systems. Constrained decoding and RAG grounding operate during generation, constraining what the LLM can output or influencing what it is likely to output, and neither inspects the finished output against an authoritative source once the generation step completes. Human-in-the-loop moves the check after generation and removes autonomy in doing so. None of the three provides an autonomous post-generation inspection, in which a deterministic component verifies each argument of a produced tool call against a domain-specific source of truth, blocks any call that fails verification, and returns feedback that lets the LLM produce a corrected call within a bounded number of attempts. Each documented approach covers one dimension of the validation problem at the expense of another. Constrained decoding prevents malformed calls and cannot detect semantic errors, being syntax-only. RAG grounding reduces the rate of semantic errors probabilistically and provides no detection mechanism for the errors that remain, and the residual error rate after grounding has not been characterized for domain-specific tool calling in Vietnamese. Human-in-the-loop catches both syntax and semantics and eliminates the autonomy that makes an AI agent worth deploying.

Arranged by the point at which each intervenes, the three approaches leave one position in the pipeline unoccupied. Constrained decoding and RAG grounding act before or during generation, shaping what the model is able or likely to emit. Human review acts after generation, but supplies its judgment from outside the system. The interval between the moment a tool call exists and the moment it executes, the only point at which a proposed action is both fully formed and not yet consequential, is occupied by nothing autonomous in any of the surveyed work. Whether it can be occupied autonomously is a question distinct from the one the three approaches answer. They address how to make a model produce wrong arguments less often. The unaddressed question is whether wrong arguments can be recognized as wrong once produced, by something other than a person, and what a system should do with that recognition.

### 2.4.6 Memory and State Management in Conversational Agents

A restaurant conversation spans multiple turns. A customer browses, asks questions, adds items, removes items, changes their mind, confirms, and pays across five to fifteen exchanges. When the customer asks in turn three about a dish mentioned in turn two, the agent has to resolve the reference. After eight turns of building a cart, the cart has to contain every item added and none of the items removed. Four strategies for maintaining dialogue history in an agent's context have been studied, each trading recall fidelity against token efficiency.

The sliding window [2.4.47] retains the most recent N messages and discards everything older. It is simple, bounded in cost, and predictable, but in a fifteen-turn conversation a ten-message window silently drops the first five turns along with any references in them. Periodic summarization, as implemented in MemGPT [2.4.48], compresses the conversation every K turns into an LLM-generated summary that replaces the raw message history in the context window, cutting token consumption at the cost of a compression step that can introduce errors. Vector-based retrieval, introduced by MemoryBank [2.4.49], embeds each turn and retrieves the most semantically similar prior turns at each new utterance, which allows targeted recall of specific exchanges without processing the full history. Hybrid approaches such as LongMem [2.4.50] combine the two, using a summary for broad conversational context and retrieved turns for specific detail from distant history.

All four operate under the same constraint, the LLM's context window. The "lost in the middle" phenomenon [2.4.28] and the attention preference for context boundaries [2.4.29] mean the model attends poorly to content in the middle regardless of how many tokens are allocated. For Vietnamese the constraint tightens further, since the tokenization penalty described in §2.4.3 applies to every stored turn: the same dialogue occupies more of the window than its English equivalent would, and the budget must additionally cover system prompts, few-shot examples, retrieved domain context, and tool-call history.

General-purpose memory frameworks do not natively separate conversation history, the text of what was said, from application state, the record of what was decided. The cart, with item names, quantities, and prices, is a structured data object rather than conversation text. The order stage (idle, building, confirming, confirmed) is a discrete state variable that gates which tools are valid. Search results from prior turns have to persist so that retrieval is not repeated. Dialogue state tracking [2.4.51] established the pattern of per-session state with explicit boundaries, and LangGraph's SQLite-backed checkpointer [2.4.13] implements it by serializing the full agent state, conversation history and application state fields together, after each node execution, keyed by session identifier.

Below: application state (cart, stage, search context) maintained as structured fields alongside conversation text.]**

General-purpose memory frameworks supply mechanisms (sliding windows, summarization, vector retrieval, checkpointing) without prescribing how to combine them for a domain whose memory holds both unstructured conversation history and persistent application state with strict correctness requirements. No prior work has characterized a memory architecture that addresses all of the following at once: retaining conversation history within the tighter token budget of Vietnamese text, holding application state as structured fields rather than reconstructing it from conversation summaries, isolating concurrent sessions strictly, and allocating the context window across system prompts, few-shot examples, conversation history, retrieved menu context, and tool-call history.

### 2.4.7 Tool Composition, Domain Adaptation, and the Cross-Domain Validation Pattern

Beyond the individual layers surveyed above, three cross-cutting concerns determine how an agent operates in practice: how it composes multiple tool calls into a valid sequence, how it is adapted to a specific domain without retraining model weights, and which architectural patterns recur across successful domain-specific agent deployments.

The foundational pattern for task-oriented agents is a single LLM selecting and calling tools from user input. ReAct [2.4.9] established sequential tool execution, where each call consumes the output of the previous one. Toolformer [2.4.52] demonstrated that LLMs learn to insert appropriate tool calls through self-supervised training on API documentation. Gorilla [2.4.53] showed accurate tool selection from large API collections after fine-tuning on synthetic tool-call data. What these systems have in common is that tool selection accuracy is well characterized. The less studied dimension is compositional correctness: whether the sequence of tool calls produces the intended final state, independently of whether each individual call was correct.

When a single utterance demands multiple tools, the composition pattern decides whether the sequence is valid. Sequential composition executes tools one after another, each consuming the previous output. It is simple to implement and debug and cannot express conditional branching, where the choice of the second tool depends on the result of the first. Parallel composition executes independent tools concurrently, which matters when an utterance carries several unrelated intents. Conditional composition routes to a second tool after a deterministic evaluation of the first tool's output: once a search returns results, the system has to determine whether the top match is exact enough to proceed to ordering, ambiguous enough to require clarification, or empty. Prior benchmarks for tool-using agents have measured per-call accuracy, how often the correct tool is selected, rather than compositional correctness, whether the resulting multi-call sequence is valid and produces the correct state [2.4.54]. Under per-call metrics, a system that calls `confirm_order` before `add_cart` scores correctly on both calls while producing an empty confirmed order. Documented tool-using agent accuracy may therefore overstate real-world reliability for transactional domains.

Prompt engineering adapts a general-purpose LLM to a specific domain without modifying model weights, which is the only feasible approach when no domain-specific training dataset exists. The standard adaptation toolkit has three techniques. System prompts define the agent's role, behavioral constraints, and output format in a fixed preamble at the beginning of the context window, where transformer attention is naturally strongest [2.4.55]. Few-shot examples demonstrate expected behavior through static input-output pairs that include both the reasoning trace and the tool call JSON, so the model sees what to call and why [2.4.56]. Dynamic context injection inserts runtime state, meaning conversation history, current application state, and prior search results, into the prompt immediately before each LLM call, which makes the agent situationally aware without encoding session-specific data into fixed prompts. DSPy [2.4.57] formalizes this as an optimization pipeline in which prompts and few-shot examples become tunable parameters optimized against an evaluation metric, moving adaptation from manual tuning to systematic search. No Vietnamese restaurant ordering dataset exists for any of these techniques, so the methods are documented but their effectiveness on Vietnamese domain-specific tool calling, where dish names, tones, and politeness registers differ from English, has not been assessed.

A recurring architectural pattern appears across safety-critical domains, independently of implementation choices. Healthcare dialogue agents [2.4.58] validate medical recommendations against drug interaction databases and dosage limits before a recommendation reaches a patient. Customer service agents [2.4.59] maintain persistent application state across turns and enforce return policies through deterministic business rules that the LLM cannot override. Code generation agents [2.4.60] validate proposed edits against test suites before committing changes, working in an edit-validate loop where the LLM proposes and the environment validates. In each case a probabilistic component proposes, a deterministic component validates against authoritative constraints, and only validated proposals become actions. The individual instances of the pattern are documented; the pattern itself has not been characterized as a general architectural requirement for systems where LLM output affects real-world state with material consequences.

The literature on conversational agents has produced capable components at every layer: architectures that govern LLM-tool interaction, models that handle Vietnamese text, routers that classify intent, and techniques for grounding generation in authoritative data. What it has not produced is an agent in which those components are integrated so that the structural constraints at each layer compensate for the probabilistic behavior of the LLM at the reasoning layer, making the whole more reliable than any of its parts.

Three integration challenges follow from the survey. The first is that the layers are interdependent in ways prior evaluations do not capture. A graph-based architecture (§2.4.2) can structurally mandate a validator node on every path between an LLM call and a tool execution, but the validator's logic, which resolves dish names against a menu database, checks state transitions, and enforces quantity bounds, is domain-specific and independent of the orchestration layer (§2.4.5). A state-augmented router (§2.4.4) can resolve context-dependent utterances, but only if the memory layer (§2.4.6) correctly maintains the application state the router reads. A prompt-only domain adaptation strategy (§2.4.7) can shape the LLM's behavior without fine-tuning, but only if the reasoning engine (§2.4.3) has enough Vietnamese capability and context window capacity to hold the system prompts, few-shot examples, and dynamic context alongside the conversation. Each layer's effectiveness depends on the layer beneath it, and no prior work has evaluated these dependencies in combination.

The second is that Vietnamese compounds the difficulty at every layer at once. Teencode abbreviations and informal variants stress the routing layer (§2.4.4) and the reasoning layer (§2.4.3) together, since the router has to classify informal utterances and the LLM has to produce tool calls using formal dish names that may differ substantially from what the customer said. Tonal diacritics and compound words stress the memory layer (§2.4.6) by consuming more tokens than their English equivalents, which shrinks the context budget available to the reasoning layer (§2.4.3) for system prompts, few-shot examples, conversation history, and retrieved menu context. The architecture layer (§2.4.2) has to work within that tighter budget while still enforcing process, validating actions, and bounding execution. No prior work has characterized how Vietnamese linguistic properties compound the design constraints each layer imposes on the others.

The third is that the validation-gated execution pattern that emerged independently across healthcare, customer service, and code generation (§2.4.7) has not been combined with the other five layers for a Vietnamese task-oriented dialogue agent. A graph-based architecture can supply the structural governance, a state-augmented router the deterministic intent classification, a post-generation validator the inspection of tool call arguments against an authoritative source, a session-scoped memory the application state across turns, and prompt-only adaptation the behavioral shaping without fine-tuning. No prior system has integrated all of them into a single agent evaluated on Vietnamese restaurant conversations. That integration, in which each layer's structural constraints address a specific failure mode of the probabilistic reasoning engine, is the primary gap this survey identifies.
