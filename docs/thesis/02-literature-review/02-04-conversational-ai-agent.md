## 2.4 Conversational AI Agent

### 2.4.1 From General-Purpose LLM to Task-Oriented Agent

Large language models (LLMs) are Transformer networks [2.4.1] scaled along parameter count, training data, and compute until performance on language tasks improves with scale in a predictable power-law relationship [2.4.2]. Trained only on next-token prediction over web-scale corpora, they turned out to be capable of translation, summarization, reasoning, and instruction following without being trained for any of them individually [2.4.3].

Whatever they can generate, LLMs remain text-in-text-out systems. They cannot modify a database, update application state, or command an external device. They map input tokens to output tokens, and those output tokens sit in a buffer until external code acts on them. The earliest way of bridging that gap was post-hoc parsing: the LLM produced a free-text instruction such as "add Ốc Hương to the cart," and a downstream parser, usually regex patterns, keyword matching, or a separately trained classifier, extracted the structured intent [2.4.4]. The pipeline was brittle, because the parser had to anticipate every phrasing the LLM might produce, and any variation broke the extraction.

Function calling [2.4.5] removed that fragility by making structured invocation a first-class capability of the LLM API itself. Instead of relying on a downstream parser, the LLM is given a schema of the available tools, each with a name, a natural-language description, and a typed JSON Schema for its parameters, and it produces a structured invocation object such as `{"name": "search", "arguments": {"query": "Ốc Hương"}}`. The serving framework intercepts that output, checks that it is syntactically correct, executes the corresponding function against live systems, and feeds the return value back to the LLM for the next reasoning step. Introduced by OpenAI and since adopted across Anthropic, Google, and Ollama [2.4.6], function calling is now the standard mechanism for turning LLM output into system actions. Figure 2.4a illustrates it.

**[Figure 2.4a. Function calling mechanism: the LLM receives a tool schema alongside the conversation and produces a structured JSON invocation rather than a free-text description; the framework executes the tool and feeds the result back.]**

Function calling provides the mechanism for action. It does not guarantee correctness. An LLM can invoke the right tool with hallucinated arguments, call tools in an invalid sequence, or produce parameter values that violate domain constraints. Whether tool invocations are safe in a transactional domain, where an error has material consequences, is settled by the layers around the LLM: the orchestration architecture, the routing mechanism, the validation gates, the memory system, and the planning logic. The subsections that follow survey each of them.

### 2.4.2 Agent Architectures: The Orchestration Layer

The architecture surrounding the LLM determines when tools can be invoked, what happens between invocations, and what the system guarantees about correctness and termination. The agent development literature has studied four architectural patterns, each governing LLM-tool interaction differently.

The simplest is the chain, in which the developer declares a fixed linear sequence of steps (classify the utterance, extract parameters, call a tool, generate a response) with no branching. As implemented in LangChain's LCEL [2.4.7], each utterance type follows its own predetermined chain, so the control flow is explicit and the execution trace is fully auditable. Prior work on chain-based task-oriented dialogue [2.4.8] reports reliable execution for narrow domains with predefined workflows. What the chain buys is deterministic governance: the developer hard-codes every step, transition, and termination condition. What it costs is rigidity. A routing error at step one is unrecoverable, because no architectural component inspects the utterance mid-chain and redirects it, and error recovery means enumerating every possible failure mode at every step, which becomes combinatorial once the input space is open-ended natural language.

The autonomous reasoning loop, introduced by the ReAct pattern [2.4.9], addresses the chain's inability to adapt to conversational variation by delegating governance to the LLM itself. On each iteration the model receives the current state (conversation history, tool definitions, and prior tool results) and produces either a reasoning trace, a tool call, or a final answer. The framework executes any tool call, feeds the result back into the loop, and the next iteration begins. AutoGPT [2.4.10] extended the pattern with internet access, file system operations, and long-term memory, which let agents pursue open-ended goals across dozens of iterations without human intervention. The loop is conversationally flexible: the LLM chooses its next action from what it observes, and the developer never enumerates dialogue paths.

That flexibility is bought by giving up the deterministic governance a chain provides. Termination is not guaranteed. The loop ends when the LLM decides to stop, and if the model enters a reasoning cycle, producing neither a tool call nor a final answer, the turn blocks indefinitely [2.4.11]. Nothing in the architecture enforces a valid tool sequence or checks tool arguments before execution. ReAct has been evaluated on knowledge-intensive benchmarks such as HotpotQA and FEVER [2.4.9], where it improved task completion rates over chain-based baselines. Its published limitations note that the architecture cannot guarantee bounded execution or action correctness, because governance and proposal reside in the same probabilistic component.

Graph-based architectures, as implemented in LangGraph [2.4.12], restore deterministic governance by encoding the state machine in the topology of the architecture rather than in prompt instructions. The developer declares a directed graph: a typed, shared state object flows through nodes (LLM calls, tool executions, or deterministic functions) connected by conditional edges that inspect the state and determine which node executes next. Unlike a chain, the graph can branch on runtime conditions. Unlike a loop, termination is structural, guaranteed by the graph topology rather than emerging from the LLM. The architecture provides three primitives: a checkpointer that serializes state after each node execution for session-scoped persistence [2.4.13], conditional edges that allow a mandatory validator node on every path between an LLM call and a tool execution, and circuit breakers that bound execution by capping retry iterations before routing to a fallback response. LangGraph has been evaluated primarily on code generation and multi-step reasoning tasks [2.4.12]; its applicability to task-oriented dialogue in Vietnamese has not been assessed.

Multi-agent architectures such as AutoGen [2.4.14], CrewAI [2.4.15], and CAMEL [2.4.16] distribute tools, prompts, and responsibilities across independent LLM instances that communicate through structured messages. The argument for the decomposition is specialization: each agent operates with a narrower scope and a more focused prompt than a single agent handling all tools [2.4.14]. Three limitations are documented. Attention dilution [2.4.17]: each agent's context window accumulates every peer agent's reasoning traces, tool outputs, and coordination instructions alongside the user utterance, and benchmarks record accuracy regression once the agent count passes two or three. Coordination is entirely LLM-mediated, since routing to a worker and handing off to a peer are themselves LLM calls, which leaves no deterministic coordination layer. And ownership of the business process is diffused across agents, with no single component structurally responsible for the correctness of the overall tool sequence.

Figure 2.4b illustrates the control flow of these four architectures.

|----------|:---:|:---:|:---:|:---:|

Only the graph row carries both of the properties this application needs at once, conversational flexibility and deterministic process enforcement, and it supplies the primitives that combine them: conditional edges for mandatory validation, circuit breakers for bounded execution, and checkpointers for session persistence. Whether those primitives are sufficient in a domain where every proposed action must be inspected before it executes has not been studied, for Vietnamese or for any other language.

The architecture also determines how several tool calls compose into a valid sequence. ReAct [2.4.9] established sequential execution, where each call consumes the output of the previous one; Toolformer [2.4.52] demonstrated that LLMs learn to insert appropriate tool calls through self-supervised training on API documentation; Gorilla [2.4.53] showed accurate tool selection from large API collections after fine-tuning on synthetic tool-call data. Across these systems tool selection accuracy is well characterized. Compositional correctness is not, meaning whether the sequence of calls produces the intended final state independently of whether each individual call was correct.

Three composition patterns are documented. Sequential composition executes tools one after another, each consuming the previous output, which is simple to debug but cannot branch on a result. Parallel composition executes independent tools concurrently, which matters when an utterance carries several unrelated intents. Conditional composition routes to a second tool after a deterministic evaluation of the first tool's output: once a search returns results, the system has to determine whether the top match is exact enough to proceed to ordering, ambiguous enough to require clarification, or empty. Only the third requires a deterministic component sitting between two LLM-proposed calls, which makes it a property of the orchestration layer rather than of the model. Prior benchmarks have measured per-call accuracy, how often the correct tool is selected, rather than compositional correctness [2.4.54]. Under per-call metrics a system that calls `confirm_order` before `add_cart` scores correctly on both calls while producing an empty confirmed order, so documented agent accuracy may overstate real-world reliability for transactional domains. ### 2.4.3 Large Language Models: The Reasoning Component

The LLM is the component that reads user input, conversation history, and system prompts and decides which tool to call and with what arguments. The literature documents three categories of Vietnamese-capable LLM, each trading language quality, function-calling capability, and deployment model against one another. Two further properties cut across the categories: the context window sets the maximum input a model can process in a single forward pass, and the serving framework determines how the model is deployed and at what cost.

The most direct approach to Vietnamese dialogue is a model trained on Vietnamese. PhoGPT (7B) [2.4.18] is a decoder-only Transformer trained from scratch on a Vietnamese-dominant corpus. On Vietnamese-specific benchmarks including VLSP [2.4.19] it produces grammatically fluent output with correct tonal diacritics and the politeness particles (dạ, ạ) that multilingual models often flatten or omit. ViSoBERT [2.4.20] is an encoder-only model based on BERT, aimed at classification and embedding rather than text generation. What these models offer is language quality: Vietnamese is their first language, in a way it cannot be for a multilingual model where Vietnamese competes with dozens of others for representation. What they lack is function calling as a first-class API capability. As of 2025, neither PhoGPT nor ViSoBERT can produce the structured `{"name": "...", "arguments": {...}}` invocation format that agent frameworks intercept and execute. They can describe in free text what action should be taken, so deploying them in a task-oriented agent would mean reverting to the post-hoc parsing architecture described in §2.4.1.

Open-weight multilingual models make the opposite trade, giving up Vietnamese-specific optimization for ecosystem maturity while remaining self-hostable. Qwen2.5 [2.4.21] emphasizes Southeast Asian languages in its training data composition, Llama 3 [2.4.22] contains approximately 0.5% Vietnamese text in its 15-trillion-token training corpus, and Gemma 2 [2.4.23] supports Vietnamese as part of its multilingual training. All three expose function calling as a documented API feature, assessed through the Berkeley Function Calling Leaderboard (BFCL) [2.4.24], a standardized benchmark measuring structured tool invocation accuracy across model families. Reported results separate the families consistently at the 7B to 9B scale, and the ordering is stable across leaderboard revisions even though the absolute figures are not, so any specific percentage must be quoted against the version that produced it. What these models give up is Vietnamese quality. Their output is correct but sometimes stilted, with occasional diacritic errors and a tendency toward a neutral register rather than a context-appropriate polite one.

Commercial API models sit at the top of the accuracy range. GPT-4o, Claude 3.5 Sonnet, and Gemini 2.0 Flash [2.4.25]–[2.4.27] combine the highest documented Vietnamese conversational quality with the highest reported BFCL results, so they satisfy language quality and function-calling accuracy at the same time, without the compromise the open-weight multilingual models make. What they impose is a deployment model: every inference call requires internet connectivity, per-token costs accumulate with usage volume, and user data travels to servers outside the operator's control.

|----------|----------------------|:---:|:---:|-------------------|:---:|
| Vietnamese-native | PhoGPT 7B, ViSoBERT | ✓ | ✗ (no API support) | Excellent (native speaker) | 4K |

The category is the stable object of comparison, not the individual models named in it, which are superseded on a timescale shorter than that of a thesis.

Context capacity varies by an order of magnitude across the table, and two documented findings bound how much that matters. Liu et al. [2.4.28] showed that performance degrades on information positioned in the middle of a long context regardless of total capacity, the "lost in the middle" phenomenon, and Xiao et al. [2.4.29] showed that transformer attention favors tokens at context boundaries; both apply across all model sizes. Vietnamese adds a further factor, since multilingual subword tokenizers are fitted predominantly on high-resource languages, so Vietnamese diacritics and compound words segment into more tokens than their English equivalents and a window of a given nominal size holds less Vietnamese conversation than the figure suggests. The size of that penalty is tokenizer-specific and is not reported for the models surveyed here [2.4.61].

Open-weight models are served through frameworks that separate by what each optimises: single-model residency behind a local HTTP API (Ollama [2.4.30]), concurrent throughput through paged key-value caching (vLLM [2.4.31]), and CPU-first inference through GGUF quantization at 4 to 8 bit precision (llama.cpp [2.4.32]). Only the last changes what the model produces. Quantization trades output quality for reduced memory, and the documented loss falls disproportionately on languages underrepresented in training data [2.4.33], which matters for Vietnamese, where tonal diacritic distinctions are the fine-grained signal most exposed to quantization noise.

Whichever model is chosen, adapting it to a specific domain without modifying its weights is the only feasible route when no domain-specific training set exists. The documented toolkit is three techniques: system prompts that fix the agent's role, constraints, and output format in a preamble at the front of the context window, where attention is strongest [2.4.55]; few-shot examples that demonstrate the expected mapping from utterance to tool call, reasoning trace included [2.4.56]; and dynamic context injection, which inserts runtime state immediately before each call so the agent is situationally aware without session data being baked into a fixed prompt. DSPy [2.4.57] formalises the three as tunable parameters optimised against a metric rather than hand-written. All three draw on the same context budget described above, and none has been assessed on Vietnamese domain-specific tool calling, where dish names, tones, and politeness registers differ from English.

The three properties have been evaluated independently across model families but never jointly. The BFCL [2.4.24] measures tool-calling accuracy on general-domain function sets in English, and no equivalent exists for domain-specific tool invocation in Vietnamese, where tool arguments carry compound dish names and tonal diacritics. The models with the best documented Vietnamese, meanwhile, are the ones evaluated on NLU benchmarks rather than on function calling [2.4.19], so the two properties this application needs together have never been measured on the same model.

### 2.4.4 Intent Classification: The Routing Layer

Before an agent can invoke a tool, it has to determine which tool the customer's utterance demands. A routing error, such as sending a menu search utterance to the ordering subsystem, produces irrelevant results at best and incorrect system actions at worst. The task-oriented dialogue literature has studied five approaches to intent routing.

The earliest train a supervised classifier on labeled utterance-intent pairs, whether keyword matching, an SVM over n-gram features, or an LSTM sequence tagger, as deployed in Rasa [2.4.34] and Dialogflow [2.4.35] and at scale for restaurant ordering in English, Chinese, Korean, and Japanese. Lightweight neural classifiers such as fastText [2.4.36] and SetFit [2.4.37] refine the same idea with subword n-gram features and few-shot fine-tuning of sentence transformers, which buys partial robustness to previously unseen words. Both families are fast (2 to 10ms) and deterministic, and both are limited in the same two ways. Their vocabulary is either manually curated or learned from formal corpora, so informal variants such as teencode abbreviations fall outside it. And each utterance is classified in isolation, with no access to prior turns: text features alone cannot separate a confirmation from a greeting, because both produce identical n-gram vectors.

Semantic centroid routing [2.4.38] encodes each intent as the mean embedding of several labeled example utterances and classifies a new input by cosine similarity to those centroids. Because the same embedding model processes the training examples and the user utterance, new vocabulary is encoded in the same space without retraining. Inference takes roughly 15ms after embedding. Published accuracy on domain-specific classification benchmarks ranges from 75% to 90% [2.4.39], and the failures concentrate in three patterns: informal variants produce embeddings far from their formal centroids, context-dependent utterances sit roughly equidistant from several centroids, and multi-intent utterances produce a blended embedding that matches none of them.

LLM-based routing [2.4.40] hands classification to the LLM, prompting it with the utterance, the conversation history, and a list of intents. Because the model met informal Vietnamese during pretraining and can attend to prior turns injected into the prompt, it handles teencode, context-dependent ambiguity, and multi-intent compounding, which are the three patterns centroid routing fails on. The documented cost is latency and non-determinism: a single classification call takes 1.5 to 2.0 seconds on consumer GPU hardware, and temperature sampling means the same utterance may route differently across calls. A less explored variation, documented in prior work on utterance rewriting [2.4.41], uses the LLM only to decompose complex or ambiguous utterances into simpler fragments and leaves the intent assignment per fragment to a separate, faster classifier. This decomposition-only use has been demonstrated on English multi-intent utterances but has not been evaluated for Vietnamese, where sentence boundaries are less clearly marked and teencode compounding creates ambiguous segmentation points.

State-augmented classification [2.4.42] keeps the fast classifier and changes its input. Rather than encoding the utterance alone, it concatenates the text representation with features read from the dialogue state, so the same words can carry different labels depending on what has already happened in the conversation. The idea is borrowed from dialogue state tracking [2.4.51], where a belief state is maintained across turns; state-augmented routing reuses that state as classifier input instead of predicting it as an output. Because the classifier remains a small supervised model, inference stays in the millisecond range and the mapping stays deterministic, so the approach retains the cost profile of the first two rows of Table 2.4c while addressing the context blindness they share.

What it costs is training data. A text-only classifier needs utterances and labels; a state-augmented one needs utterances, labels, and the dialogue state each utterance was spoken in, which multiplies the annotation effort and ties the corpus to one application's state schema. Published evaluations are on English task-oriented dialogue [2.4.63], and no Vietnamese corpus carrying state annotations exists.

Across all five the same trade recurs. The mechanisms that are fast and deterministic are precisely those blind to informality, dialogue context, and multi-intent structure, and the one mechanism that handles all three is slow and non-deterministic. Neither variant at the margins escapes it: decomposition-only LLM use [2.4.41] has not been evaluated on Vietnamese, where teencode compounds create ambiguous segmentation boundaries, and state augmentation buys dialogue context at the price of a corpus that does not exist for this language.

The surveyed work treats this trade as a property of the choice itself, positioning the approaches along a single axis from cheap and brittle to expensive and flexible. What it does not ask is whether the two halves are separable: whether the cases that defeat a classifier are frequent enough, or distinguishable enough in advance, to warrant a different mechanism from the cases that do not. The existing evidence for Vietnamese could not settle the question either, since compound dish names, tonal diacritics, context-dependent affirmations, and teencode abbreviations each aggravate a different one of the five documented limitations, and no approach has been evaluated on speech carrying those properties.

### 2.4.5 Action Validation: The Safety Layer

Correct routing ensures the right tool is called. It does not ensure the tool is called with correct arguments. An LLM that routes an utterance to the ordering subsystem may still produce `add_cart(name="Pizza Hải Sản", quantity=1)`, a call that is syntactically valid JSON and semantically wrong, because the named dish does not exist on the menu. Function calling guarantees syntactic validity; semantic correctness requires a separate mechanism. Three approaches to argument-level errors have been studied, each intervening at a different point in the generation pipeline [2.4.62].

The earliest and simplest defense is constrained decoding [2.4.43], which enforces JSON schema compliance at the token generation level: the serving infrastructure restricts the LLM's output vocabulary at each generation step to tokens consistent with the target schema, so field names, types, required fields, and value constraints match the tool definition. The guarantee is syntactic. `{"name": "Pizza Hải Sản", "quantity": 1}` satisfies every schema constraint, because `name` is a valid string and `quantity` a valid integer, and neither value has been checked against any external source of truth. Constrained decoding can stop the LLM producing a malformed tool call. It cannot stop it producing a well-formed call with wrong arguments.

Retrieval-augmented generation grounding [2.4.44] addresses the semantic gap that constrained decoding leaves open by injecting the authoritative data, for a restaurant the actual menu, into the LLM's prompt before it generates tool arguments. With valid dish names and prices in the prompt, the model is more likely to reproduce those exact strings than to fabricate alternatives. Asirvatham et al. [2.4.45] demonstrated that RAG grounding reduces hallucination rates in knowledge-intensive tasks without eliminating them: the LLM may attend to the wrong portion of the prompt, prioritize pretraining knowledge over the injected context, or select a nearby but incorrect value from the retrieved data. Grounding lowers the probability of error and supplies no mechanism for detecting which specific tool calls remain incorrect, so the system cannot distinguish a grounded correct call from an ungrounded hallucination.

Human-in-the-loop approval [2.4.46] attacks the same problem from the other end. Rather than preventing or reducing errors during generation, it requires a human operator to review each tool call before execution and either approve or reject it. Hallucination risk disappears, since every argument is verified against a person's knowledge of the domain and no incorrect call reaches an external system. The approach has been deployed in high-stakes decision-support systems where the cost of an error justifies the cost of human review [2.4.46]. What it gives up is not accuracy but autonomy: the system requires human staffing for every action, which limits it to domains where full automation is not the objective.

All three share a structural property that limits their effectiveness for autonomous systems. The first two act during generation and never inspect the finished output against an authoritative source; the third inspects it but supplies the judgment from outside the system. None of them provides an autonomous post-generation inspection, in which a deterministic component verifies each argument of a produced tool call against a domain-specific source of truth, blocks any call that fails verification, and returns feedback that lets the LLM produce a corrected call within a bounded number of attempts. The pattern those three approaches do not implement is nonetheless established elsewhere. Healthcare dialogue agents [2.4.58] check medical recommendations against drug interaction databases and dosage limits before a recommendation reaches a patient. Customer service agents [2.4.59] enforce return policies through deterministic business rules the LLM cannot override. Code generation agents [2.4.60] validate proposed edits against a test suite before committing them, in a loop where the model proposes and the environment judges. In each case a probabilistic component proposes, a deterministic component checks the proposal against an authoritative constraint, and only what passes becomes an action. The instances are documented individually; what has not been characterized is the pattern as a general requirement for systems whose LLM output changes real-world state.

The interval between the moment a tool call exists and the moment it executes, the only point at which a proposed action is both fully formed and not yet consequential, is occupied by nothing autonomous in any of the surveyed work. All three approaches address how to make a model produce wrong arguments less often. The question none of them answers is whether wrong arguments can be recognized as wrong once produced, by something other than a person, and what a system should do with that recognition.

### 2.4.6 Memory and State Management in Conversational Agents

A restaurant conversation spans multiple turns. A customer browses, asks questions, adds items, removes items, changes their mind, confirms, and pays across five to fifteen exchanges. When the customer asks in turn three about a dish mentioned in turn two, the agent has to resolve the reference. After eight turns of building a cart, the cart has to contain every item added and none of the items removed. Four strategies for maintaining dialogue history in an agent's context have been studied, each trading recall fidelity against token efficiency.

The sliding window [2.4.47] retains the most recent N messages and discards everything older. It is simple, bounded in cost, and predictable, but in a fifteen-turn conversation a ten-message window silently drops the first five turns along with any references in them. Periodic summarization, as implemented in MemGPT [2.4.48], compresses the conversation every K turns into an LLM-generated summary that replaces the raw message history in the context window, cutting token consumption at the cost of a compression step that can introduce errors. Vector-based retrieval, introduced by MemoryBank [2.4.49], embeds each turn and retrieves the most semantically similar prior turns at each new utterance, which allows targeted recall of specific exchanges without processing the full history. Hybrid approaches such as LongMem [2.4.50] combine the two, using a summary for broad conversational context and retrieved turns for specific detail from distant history. Figure 2.4f sets the four side by side.

All four operate under the same constraint, the LLM's context window. The "lost in the middle" phenomenon [2.4.28] and the attention preference for context boundaries [2.4.29] mean the model attends poorly to content in the middle regardless of how many tokens are allocated. For Vietnamese the constraint tightens further, since the tokenization penalty described in §2.4.3 applies to every stored turn: the same dialogue occupies more of the window than its English equivalent would, and the budget must additionally cover system prompts, few-shot examples, retrieved domain context, and tool-call history.

General-purpose memory frameworks do not natively separate conversation history, the text of what was said, from application state, the record of what was decided. The cart is a structured data object rather than conversation text; the order stage (idle, building, confirming, confirmed) is a discrete variable that gates which tools are valid; search results from prior turns have to persist so that retrieval is not repeated. Dialogue state tracking [2.4.51] established the pattern of per-session state with explicit boundaries, and LangGraph's SQLite-backed checkpointer [2.4.13] implements it by serializing the full agent state after each node execution, keyed by session identifier.

**[Figure 2.4f. Memory strategies in conversational agents: (a) sliding window discards older turns; (b) periodic summarization compresses history; (c) vector retrieval selects relevant past turns; (d) hybrid combines summary with retrieval. Below: application state (cart, stage, search context) maintained as structured fields alongside conversation text.]**

What none of the four strategies prescribes is the separation this domain requires. Conversation history tolerates lossy compression, because a summarized turn still conveys what was discussed. Application state does not: a cart compressed to *the customer ordered some seafood and a beer* cannot be priced, confirmed, or billed. The two kinds of memory therefore cannot share a storage strategy, and none of the surveyed work treats them as distinct.

---

The literature on conversational agents has produced capable components at every layer: architectures that govern LLM-tool interaction, models that handle Vietnamese text, routers that classify intent, and techniques for grounding generation in authoritative data. What it has not produced is an agent in which those components are integrated so that the structural constraints at each layer compensate for the probabilistic behavior of the LLM at the reasoning layer, making the whole more reliable than any of its parts.

The layers are interdependent in ways the individual evaluations cannot capture, because each one's effectiveness rests on the layer beneath it. A graph architecture can structurally mandate a validator on every path from an LLM call to a tool execution, but what that validator checks is domain-specific and owes nothing to the orchestration layer. A state-augmented router can resolve a context-dependent utterance only if the memory layer maintains the state it reads. Prompt-only adaptation can shape behaviour without fine-tuning only if the reasoning engine has the Vietnamese capability and the context capacity to hold the prompts, the examples, and the conversation at once, and Vietnamese tightens that budget at the same time as it stresses the routing layer with teencode and the reasoning layer with compound dish names. The validation-gated pattern that emerged independently across healthcare, customer service, and code generation is the missing piece that would hold the rest together, and no prior system has combined it with the other five layers for a Vietnamese task-oriented agent. That integration, in which each layer's structural constraints address a specific failure mode of the probabilistic reasoning engine, is the primary gap this survey identifies.
