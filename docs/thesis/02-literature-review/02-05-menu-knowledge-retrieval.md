## 2.5 Menu Knowledge Retrieval (RAG)

### 2.5.1 The Knowledge Problem and Standard RAG

Large language models are trained on public web data frozen at a point in time, and a restaurant's menu, with its particular dish names, local ingredients, seasonal items, and prices, appears nowhere in that distribution. Asked about knowledge it does not have, a model produces confident and incorrect output, a failure documented as closed-book hallucination [2.5.1]. Retrieval-augmented generation (RAG), introduced by Lewis et al. [2.5.2], separates knowledge from model parameters by inserting a retrieval step before generation: the corpus is embedded into a vector index offline, the query is embedded with the same encoder at run time, the nearest documents are retrieved, and they enter the prompt as grounding context. The arrangement has become the dominant approach for knowledge-intensive tasks including open-domain question answering [2.5.3], fact verification [2.5.4], and domain-specific dialogue [2.5.5].

The survey literature distinguishes three generations of this pipeline [2.5.6]. Naive RAG is the arrangement just described. Advanced RAG improves individual stages, through better chunk boundaries, re-ranking of the retrieved set, or expansion of the query before it is embedded, without altering the architecture. Modular RAG [2.5.7] makes the stages independent and swappable, a retriever, a rewriter, an evaluator, and a generator, so each can be optimized per domain. What modularity does not supply is coordination. The composition is configurable, but nothing in the documented architecture decides whether a module's output is adequate, whether another module should run, or whether retrieval has failed.

All three share one structural assumption: that the query embedding lies near the embeddings of the documents that answer it. The assumption holds when query and documents share vocabulary. It fails when the information need is expressed in terms the corpus does not contain, a failure documented as query-document vocabulary mismatch [2.5.8]. The mismatch is structural rather than a matter of index quality, encoder choice, or chunk strategy, because the two sets of vectors occupy disconnected regions of the space, and improving any single stage cannot repair it. Repair would require a component that inspects the query, recognizes the gap, and transforms the query into terms the document space can match, before retrieval runs.

A second property is easier to see once the three variants are set beside one another. In each, information travels one way: the query into a retrieval, the retrieval into a set of documents, the documents into a prompt, the prompt into text. The model occupies the last position. It receives whatever retrieval returned, had no part in deciding how that retrieval was conducted, and has no means of registering that what came back was unusable. Naive RAG establishes this order, advanced RAG improves the quality of each stage within it, and modular RAG makes the stages swappable without altering the direction in which they are connected. The vocabulary mismatch is therefore a failure the architecture provides no position to detect, since detection would require the component best able to judge relevance to sit somewhere other than at the end.

### 2.5.2 Representing Vietnamese Text for Retrieval

Two paradigms turn text into something comparable for relevance. Dense embeddings place text in a learned continuous space; sparse representations weight vocabulary terms by frequency statistics. Vietnamese word segmentation is a prerequisite for both, and it is one the language imposes rather than the method.

Vietnamese script places spaces between syllables, not between words. A three-syllable compound such as "bún bò Huế" is written as three space-separated tokens but names one dish. Without segmentation a dense model embeds three fragments rather than the compound, and a sparse index treats the three as independent terms, so a query containing "bò" matches any document containing that syllable. Table 2.5a lists the three tools documented for the task [2.5.9].

**Table 2.5a.** Vietnamese word segmentation tools.

| Tool | Method | Accuracy (VLSP 2013) | Deployment | Documented limitations |
|------|--------|:---:|---|---|
| `underthesea` | CRF, Vietnamese Treebank | ~97% | Pure Python, ~50 MB | Accuracy on informal and elided forms unbenchmarked; domain-specific proper nouns not evaluated |
| `VnCoreNLP` | RNN + word embeddings + CRF | Higher (~98%+) | Java (separate process) | Java runtime dependency; per-call process overhead compared with in-process alternatives |
| `pyvi` | Dictionary + regex | Lower | Pure Python, no model | Weak on compound terms with ambiguous boundaries; dictionary coverage limited |

The accuracies in the table are measured on formal written Vietnamese. No published evaluation covers domain-specific proper nouns, which is where a segmenter's dictionary and statistical model are least reliable, and a menu is composed almost entirely of proper nouns.

Dense encoders for Vietnamese fall into two categories, and the axis between them runs from language fidelity to ecosystem maturity. Vietnamese-native bi-encoders [2.5.10]–[2.5.14] are built on PhoBERT [2.5.11] or comparable monolingual encoders, so their tokenizers preserve diacritics without the subword boundary artifacts that multilingual BPE introduces, and their training corpora include the informal registers of social media and forums. They report gains of 8 % to 15 % over multilingual alternatives on Vietnamese sentence-similarity benchmarks [2.5.15]. Retrieval-specific results, measured over document collections rather than sentence pairs, are unreported for the category. Multilingual models [2.5.16]–[2.5.18] lead cross-lingual retrieval benchmarks and provide features the Vietnamese-native models lack natively, such as multi-vector retrieval, with diacritic handling that is adequate rather than tuned: the tokenizers preserve diacritic-bearing characters but allocate no attention specifically to tonal distinctions, and compound-word boundaries are not recognized as units distinct from syllable spans.

**Table 2.5b.** Dense embedding models with Vietnamese capability.

| Model | Dim | Vietnamese-native | Diacritic-aware | Parameters | Documented strengths | Documented limitations |

Where neither category is characterised is on the kind of corpus a menu constitutes. The cross-lingual benchmarks the multilingual models are evaluated against, MIRACL and MTEB, are built from news articles and encyclopedia entries: documents of several hundred tokens whose vocabulary and term-frequency distributions approximate general language. A menu is the opposite kind of corpus in every respect that retrieval depends on. Its documents are short and structurally uniform, its vocabulary is dominated by proper nouns that appear in no general corpus, and the terms distinguishing two entries from one another may amount to a single word. No published retrieval evaluation, for either category of model, uses a corpus with those properties.

The sparse alternative is BM25 [2.5.19], which extends the TF-IDF framework with two tunable parameters: k₁ saturates the contribution of a repeated term, so a term appearing fifty times does not score ten times a term appearing five times, and b controls how far document length is normalized away, applied in full at b = 1 and removed entirely at b = 0. What BM25 does well is exact lexical matching, with strong separation between documents that contain the query terms and documents that do not. What it cannot do is bridge a vocabulary gap: a query sharing no term with the index returns nothing, whatever the parameter values, because a sparse representation has no mechanism for crossing a lexical gap. For Vietnamese its behaviour is decided upstream by the segmenter, since mis-segmented compounds fragment into syllables that then match across unrelated dishes, and the interaction between segmentation quality and retrieval precision has not been systematically studied for Vietnamese domain-specific corpora.

Both representations need an index. Dense vectors are searched with FAISS [2.5.20], which provides exact search at a cost linear in corpus size alongside approximate structures that reduce that cost in exchange for occasionally missing the true nearest neighbour; at a corpus of a few hundred documents the exact option costs nothing, so the choice among index structures is not a live question at this scale. The sparse side uses an inverted index, mapping each term to the documents containing it, which is the foundational data structure of information retrieval and is validated across decades of evaluation at TREC, CLEF, and NTCIR [2.5.21].

### 2.5.3 Result Fusion

When a dense and a sparse retriever run in parallel they produce two ranked lists that have to become one, and the scores cannot simply be added: BM25 scores are unbounded term-weight sums while cosine similarities are bounded in [−1, 1], and the two ranges carry no common meaning. Three fusion techniques from the information retrieval literature handle that incommensurability differently.

Reciprocal Rank Fusion (RRF), introduced by Cormack et al. [2.5.22] for meta-search evaluation, avoids the normalization problem by operating on ranks rather than raw scores. Each document's fused score is the sum, across the lists it appears in, of the reciprocal of its rank shifted by a constant k, conventionally set to 60. The method needs no score normalization, no domain-specific tuning, and no assumption about score distributions, and a document appearing in only one list is not penalized beyond the missing contribution from the other, so it can still rank highly if its single-list rank is competitive.

Linear combination normalizes the scores, typically by min-max scaling or z-score standardization, then sums them under a weight α controlling each retriever's contribution. Where α is well calibrated for a specific domain and collection, it can achieve higher accuracy than RRF, because it exploits the score magnitude information RRF discards [2.5.23]. The weight does not transfer: one tuned on news articles will not be optimal for menu entries, and without domain-specific calibration data the method can underperform RRF, because magnitude differences that carry no meaningful signal are amplified by the weight.

Condorcet voting [2.5.24] treats fusion as a pairwise comparison, ranking each document by how many others it beats across the lists. It requires no normalization and extends naturally beyond two retrievers, but costs O(n²) in the number of unique documents, and for two-retriever fusion no evaluation has demonstrated a systematic advantage over the simpler and faster RRF baseline.

**Table 2.5c.** Fusion methods for combining ranked lists from several retrievers.

| Method | Score normalization | Domain transfer | Computational cost | Single-list documents |
|--------|:---:|:---:|:---:|---|
| RRF | Not required; operates on ranks | Domain-independent (k = 60 is fixed; no per-domain tuning needed) | O(n log n) for sorting n unique documents | Receive contribution from one retriever; no penalty for absence from other lists |
| Linear combination | Required; min-max or z-score per retriever | Weight α must be re-tuned per domain and document collection | O(n) after normalization | Score depends on normalization of the present retriever; absent retriever contributes 0 |
| Condorcet voting | Not required; uses pairwise rank comparisons | Domain-independent | O(n²) for n unique documents | Win against documents ranked lower in all lists where both appear; absent documents lose all pairings |

### 2.5.4 Beyond Retrieve-then-Generate: Rewriting, Evaluation, Context

The standard pipeline runs one way: retrieval produces a ranked list and the model consumes it. Three classes of extension have been proposed against pieces of that limitation, one before retrieval, one after it, and one across turns. Each has been evaluated as an independent point solution on English benchmarks.

Pre-retrieval query rewriting transforms the query before it reaches the retriever, and two techniques are documented, each bridging the vocabulary gap by a different mechanism.

HyDE (Hypothetical Document Embeddings), introduced by Gao et al. [2.5.25], prompts a model to generate a plausible relevant document and embeds that hypothetical document for retrieval in place of the raw query. The premise is that generated text, even where factually wrong, shares vocabulary and structure with real documents in the target corpus, while the user's natural-language query may come from a different register. Evaluated on TREC DL and Web Questions, HyDE improved retrieval recall on vocabulary-gap queries in English. Its documented limitation is unbounded generation: the model may fabricate terms, entities, or categories absent from the real corpus, and the hypothetical document's embedding then pulls retrieval toward the fabrication rather than toward genuinely relevant documents.

Step-Back Prompting, introduced by Zheng et al. [2.5.26] for reasoning tasks and later adapted to retrieval, abstracts the query to a higher conceptual level and retrieves against the abstraction instead. Because the model produces a category or a more general question rather than free-form text, the hallucination risk is lower than HyDE's, but the approach depends on the model choosing the right level: too abstract and retrieval loses specificity, too specific and the vocabulary gap persists. It has been evaluated on MMLU and TimeQA in English, where the abstraction runs over factual taxonomy, from a particular event to the class it belongs to, and where one step-back question is produced per query. Neither property is guaranteed to carry over to a menu, since a description of how a dish should feel to eat may correspond to several unrelated categories at once, and the mapping from sensation to category is a culinary association held by a culture rather than a fact recorded in text. Whether a model holds such associations reliably is a question no published evaluation addresses.

Both share a structural property that keeps them out of a control loop: they transform the query and then hand off to retrieval, with no return path. The model that performed the rewriting never sees the retrieved results, cannot evaluate whether the rewrite helped or hurt, and cannot adjust its strategy from retrieval quality. The rewriting is an open-loop transformation.

Post-retrieval evaluation inspects the retrieved documents after retrieval and before generation, filtering noise and, in some architectures, triggering corrective action.

Self-RAG, introduced by Asai et al. [2.5.27], uses reflection tokens, special tokens the model learns to generate during fine-tuning, indicating whether each retrieved passage is relevant and whether the generated text is supported by it. Quality assessment is embedded in generation, which allows per-passage filtering without a separate evaluation model. Its primary limitation is the fine-tuning requirement: the reflection tokens have to be trained into the model's vocabulary and output distribution, which takes training infrastructure and labelled data that most domain-specific deployments do not have.

CRAG (Corrective RAG), introduced by Yan et al. [2.5.28], scores relevance at inference time instead. The model rates each retrieved document on a numeric scale, documents below a threshold are discarded, and a fallback is triggered if nothing passes. The approach adds one model call per retrieval and has been evaluated on English QA benchmarks including PopQA, PubHealth, and Arc-Challenge. Its corrective action is predetermined rather than strategy-aware: the fallback is a web search, and the model does not decide what kind of search to run next or how to modify its approach.

Neither has been evaluated on domain-specific retrieval where relevance depends on structured metadata matching, that is on whether a dish's ingredients, taste profile, and preparation method fit a sensory description, rather than on factual concordance with a knowledge base.

Multi-turn search context addresses a limitation specific to conversational retrieval. Within one session a user may issue several related queries, and a user who searches in turn 3 and then refers back pronominally in turn 6 ("cái đó có cay không?") expects the reference resolved against prior results rather than a fresh retrieval on the literal string. Dialogue state tracking [2.5.29] maintains structured per-session state, but it was designed for finite-state and frame-based architectures holding scalar slot values, where a retrieval result is a ranked list with metadata. Memory-augmented RAG architectures including MemoryBank [2.5.30] and LongMem [2.5.31] persist retrieved context across conversations, but for cross-session user modelling, remembering preferences over weeks, rather than for deduplication within a single visit. No prior extension addresses the entity resolution problem specific to multi-turn retrieval: determining whether a new utterance refers to a previously retrieved item and answering from memory instead of re-querying.

Set beside one another the three extensions share a property none of them reveals alone. Query rewriting acts before retrieval and hands off without a return path. Post-retrieval evaluation acts after retrieval and, where it takes corrective action at all, takes one fixed in advance rather than chosen in response to what came back. Multi-turn context persists across turns without informing the retrieval inside any of them. Each attaches to an edge of the pipeline, and none produces a signal travelling from the output of retrieval back to its input, which is why a pipeline with all three installed still cannot register that a retrieval failed and then do something different in consequence. Whether that connection is constructible, and if so which component is positioned to judge, given that judging requires understanding both the information need and the documents returned, is not a question the surveyed work takes up.

---

The gap this survey ends on was opened by the fix for an earlier one. Modular RAG answered a real complaint: the naive pipeline was rigid, and making its stages independent and swappable let each be optimized for a domain without disturbing the others. Independence was the point. But independence was achieved by specifying what each module hands to its neighbours and leaving unspecified what any module should do about what it receives, so a module returning poor output and a module returning good output present the same interface. The pattern that made the components composable is the same pattern that omits coordination, which is why the extensions of §2.5.4 attach so readily to the pipeline's edges while none of them closes it.

What the pipeline lacks is a component that is not a well-behaved module: something that reads the output of a stage and decides what happens next. The vocabulary mismatch of §2.5.1 gives that absence its concrete form, since bridging a sensory query to a corpus indexed by name requires knowledge about the domain, and the only component holding that knowledge is the one placed last and consulted never.
